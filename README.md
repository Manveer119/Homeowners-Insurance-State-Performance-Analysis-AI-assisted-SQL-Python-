# Homeowners Insurance State Performance Analysis

An AI-assisted pricing and risk analysis of a **synthetic** homeowners insurance book across 8 states: 60,000 quotes, 14,046 policies, and 987 claims. The analysis asks one question: **where can the book grow profitably, and where does pricing or underwriting need attention?**

> **Data note:** All data is synthetic, generated by `src/generate_data.py` with a fixed seed. No real company or customer data is used. Risk patterns were built in deliberately so the analysis has realistic signals to find.

## Key findings

| # | Finding | Evidence |
|---|---|---|
| 1 | **Texas is the only state above the 65% loss ratio target** | 66.3% loss ratio, highest claim frequency (10.2 claims per 100 policies), 2nd-largest book ($6.8M premium) |
| 2 | **Coastal homes with 21+ year roofs lose money** | 108% loss ratio: $1.99M in losses on $1.84M premium. Inland 21+ roofs run 65%; inland 0–5 year roofs run 30% |
| 3 | **GA, SC, AZ, and NC are profitable growth candidates** | Loss ratios of 40–51% with above-average quote-to-bind (24.6–26.3% vs. 23.4% book average) |
| 4 | **Virginia is profitable but under-converting** | 46% loss ratio, yet 22.0% quote-to-bind is below average, which suggests a price-competitiveness gap worth reviewing |
| 5 | **The Partner channel underperforms everywhere** | Lowest quote-to-bind in all 8 states (14.8–18.4% vs. 24.9–31.5% for Agent) and lowest retention (72–80%) |

See [`FINDINGS.md`](FINDINGS.md) for recommendations and the Texas rate-change scenario.

## Metrics

| Metric | Definition |
|---|---|
| Quote-to-bind | Bound quotes ÷ total quotes |
| Written premium | Sum of premium on bound policies |
| Retention | Share of policies that renewed |
| Loss ratio | Incurred losses ÷ written premium (premium treated as fully earned over a 12-month term) |
| Frequency | Claims per 100 policies |
| Severity | Average incurred loss per claim |

The 65% loss ratio target is an assumed benchmark for this exercise, not an industry standard.

## How AI was used, and how it was checked

I used Claude as a coding assistant to draft the SQL queries, Python analysis, and chart code. AI-generated code was treated as a draft, never as a result. Every output was validated before it informed a finding.

**Validation (27 automated checks, all passing; see `outputs/validation_results.csv`):**
- **Data quality:** unique IDs, every bound quote maps to exactly one policy, no orphan claims, no missing values, no claim above Coverage A, all loss dates inside the policy term.
- **Independent recomputation:** every metric in the SQL state scorecard and segment tables is recalculated separately in pandas and must match.
- **Tie-outs:** segment premium and losses must sum to book totals, and channel binds must sum to total binds. This guards against join fan-out, where a policy with several claims gets its premium counted more than once.
- **Output review:** reading the results caught a sorting bug. Roof-age bands sorted as text, so "6-10" appeared after "21+". The fix was an explicit `CASE` sort, plus a new automated check so the bug can't come back.

**Known limitations:**
- Claim counts per state are small (58–260 claims), so state-level loss ratios are directional, not credible enough for a rate filing.
- The rate scenario uses an assumed price elasticity, not one estimated from data, and assumes no adverse selection.
- Premium is treated as fully earned; a production analysis would use earned premium and loss development.

## Run it

```bash
pip install -r requirements.txt
python src/generate_data.py
python src/analysis.py
```

`analysis.py` stops with an error if any validation check fails.

**Tools:** SQL (SQLite), Python (pandas, NumPy, matplotlib), Claude (AI coding assistant)
